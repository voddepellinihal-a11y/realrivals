## Important product constraints

-   The application is intended to be deployed publicly.
-   The landing page and authentication pages may be public.
-   All competition features and private user/group data require login.
-   Email verification is required before normal application access.
-   Backend authorization is mandatory; frontend route guards alone are
    insufficient.
-   XP, streaks, achievements, race positions, and final rankings are
    server-authoritative.
-   Proof media must use private object storage.
-   Start with a modular monolith; do not introduce microservices
    prematurely.

## Development instruction

Read all five documents before implementing features. Treat them as the
initial project specification. If requirements conflict or are
ambiguous, document the conflict and resolve it before coding.

# Running the app

## Local development

```bash
# 1. API  (http://127.0.0.1:8000)
cd backend
pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 2. SPA  (http://127.0.0.1:5173) — optional, the API serves the built app too
cd frontend
npm install
npm run dev
```

The API serves `frontend/dist` at `/`, so a single `npm run build` is enough to
browse the whole app on port 8000.

```bash
cd frontend && npm install && npm run build
```

## Tests

```bash
cd backend
python -m pytest -q                              # unit + API tests
python tests/verify_master_task.py               # end-to-end flow against a running server
python tests/verify_production_boot.py           # simulates the Render production boot
python tests/verify_public_startup.py <url>      # smoke-test a deployed instance
python tests/verify_login.py <url> <email> <pw>  # log in and load the dashboard
```

`verify_master_task.py` needs the two seeded account passwords. Put them in
`backend/.env` (git-ignored) or export them first:

```bash
set RIVAL1_PASSWORD=... && set RIVAL2_PASSWORD=...
python tests/verify_master_task.py
```

# Deploying to Render (24/7 public access)

`render.yaml` at the repository root is a [Render Blueprint][blueprint]. It
builds the SPA, installs the API dependencies, applies the database migrations
and starts a single FastAPI process that serves both the API and the built
frontend from one origin.

[blueprint]: https://render.com/docs/blueprint-spec

## Deploy

1. Push the repository to GitHub (Render reads the Blueprint from the repo root).
2. In Render: **New → Blueprint** → select the repo → Render reads `render.yaml`.
3. Fill in the prompted values:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | Your Supabase **connection pooler** URL (port `6543`). The direct host on port `5432` is not reachable from Render's network. |
   | `SMTP_HOST` / `SMTP_USERNAME` / `SMTP_PASSWORD` / `SMTP_FROM_EMAIL` | Optional, but without them verification and password-reset emails are never delivered. |

   `JWT_SECRET_KEY` is generated by Render (`generateValue: true`), so it never
   has to be copied around. The same is true for `RIVAL1_PASSWORD` /
   `RIVAL2_PASSWORD` — the two seeded account passwords are generated, not
   committed, so the public repository never leaks a way into the instance.
   **Read them from the service's Environment tab** to log in.

4. Deploy. The public URL is `https://real-life-rivals.onrender.com`.

### One extra step: rotate the seeded account passwords

The two private accounts are created on the **first** boot. Your database
already contains them, so the passwords Render generated are **not** applied
automatically — the old ones would keep working. Rotate them once, locally,
using the same values you set on Render:

```bash
cd backend
set RIVAL1_PASSWORD=... && set RIVAL2_PASSWORD=...
python -m app.db.rotate_seeded_passwords
```

Do this before sharing the public URL with anyone.

## What the blueprint configures

| Setting | Value | Why |
| --- | --- | --- |
| `runtime` | `python` | The Blueprint key for Python (the older `env: python` form is rejected). |
| `buildCommand` | build SPA → install deps → check DB → `alembic upgrade head` | Migrations run before the new version serves traffic. |
| `startCommand` | `uvicorn app.main:app --host 0.0.0.0 --port $PORT` | Binds to Render's dynamic port. |
| `healthCheckPath` | `/health` | Liveness probe (does not touch the database, so a DB hiccup never restarts the service). |
| `plan` | `free` | Change to `1c-2g` for a permanently warm service (free instances idle after ~15 min). |
| `ENVIRONMENT` | `production` | Turns on the production secret checks. |
| `FRONTEND_URL` | self-referencing `RENDER_EXTERNAL_URL` | Links in emails point at the deployed site. |

## Troubleshooting a failed deploy

### `alembic upgrade head` exits with status 1

The build runs a pre-flight check first, so the log tells you what is wrong:

```
Database: postgresql+psycopg2://postgres.xxx:***@aws-0-<region>.pooler.supabase.com:6543/postgres
TCP:      reachable at aws-0-<region>.pooler.supabase.com:6543
Query:    SELECT 1 succeeded
```

| Log says | Cause | Fix |
| --- | --- | --- |
| `DATABASE_URL is not set` | The variable was never filled in | Set it in Render's Environment tab |
| `TCP: FAILED to reach …` | The host is not reachable from Render | Use the **connection pooler** URL (port `6543`), not the direct host (`5432`) — Render's outbound addresses are dynamic and IPv4-only |
| `Can't load plugin: sqlalchemy.dialects:postgres` | The URL uses `postgres://` | Already handled — the URL is normalised automatically |
| `No module named 'psycopg'` | The URL uses `postgresql://` without a driver | Already handled — normalised to `postgresql+psycopg2://` |
| `invalid interpolation syntax` | The password contains `%` | Already handled — the URL is escaped for ConfigParser |
| `Query: FAILED` | Wrong password / database / role | URL-encode `@` as `%40` and `$` as `%24` |

Run the same check locally:

```bash
cd backend
python -m app.db.check_database
```

### Verify a deployed instance

```bash
cd backend
python tests/verify_public_startup.py https://real-life-rivals.onrender.com
python tests/verify_login.py https://real-life-rivals.onrender.com rival1@realliferivals.com <password>
```

### The app starts but the page is blank

`GET /health` returns `{"status":"ok"}` and `/health/ready` returns
`{"status":"ready","database":"connected"}`. If the SPA is missing, the build
did not produce `frontend/dist` — check the build log for the `npm run build`
step.

## Environment variables

| Variable | Required | Notes |
| --- | --- | --- |
| `DATABASE_URL` | yes | Supabase pooler URL, `sslmode=require`. |
| `JWT_SECRET_KEY` | yes in production | ≥ 32 bytes. Render generates it. The app **refuses to boot** in production without it. |
| `RIVAL1_PASSWORD` / `RIVAL2_PASSWORD` | yes in production | Passwords for the two seeded accounts. Render generates them; in production the seeder refuses to invent its own. |
| `ENVIRONMENT` | — | `production` enables the strict secret checks. |
| `CORS_ORIGINS` | — | Comma separated; `*` (the default) allows every domain. |
| `FRONTEND_URL` | — | Public URL used in emails; falls back to `RENDER_EXTERNAL_URL`. |
| `SMTP_*` | — | Needed for verification / reset emails. |

Unknown variables are ignored, so provider-injected ones never break startup.

## Routing notes

* The SPA is mounted at `/` and unknown client-side paths (`/login`,
  `/dashboard`, `/onboarding`, …) fall back to `index.html` with a `200`, so a
  hard refresh never 404s.
* Paths that belong to the API (`/auth/*`, `/challenges/*`, `/routines/*`,
  `/submissions/*`, `/game/*`, `/user/*`, `/groups/*`, `/health*`) still return
  JSON — an unknown API path is a `404`, not the HTML shell.
* `index.html` is served `no-cache`; content-hashed assets under `/assets` are
  served `immutable` for a year, so a redeploy is picked up immediately instead
  of serving a stale bundle.
